ChessGuru data lineage

How data flows from chess.com to the dashboard. Arrows point from a source to the table built from it. Everything lives in one DuckDB file (chessguru.duckdb) except the raw month files.

Bronze: raw files Silver: cleaned tables (Python) dbt views (staging, intermediate) Gold: tables the dashboard reads Dashboard Housekeeping

What each step does

StepCodeReadsWritesWhat happens
fetchingest/fetch.py, api/client.pychess.com Published-Data APIBronze month files Downloads months newest first until there are enough games. A month is reused only if it was downloaded after it ended.
checkquality/checks.pyBronze month filesquarantine Validates every game against the data contract. Bad games are set aside with a reason; the run stops if over half break the contract.
parseparse/games.py, parse/silver.pyChecked gamessilver_games, silver_moves, quarantine One row per game from your side, one row per move. Opponent names are not kept.
analyseanalysis/silver_games, silver_movessilver_move_evals, silver_game_analysis Stockfish scores every position. Each move gets a win-chance drop, label, accuracy, phase and reason tags.
buildtransform/dbt.py, dbt/The four silver tablesStaging and intermediate views, gold tables dbt renames and joins the silver tables, adds the low_clock tag and per-game counts, and tests the result.
dashboardapp/data.pyGold tables, quarantine, pipeline_runs, silver row countsNothing Read-only queries. Filters, summaries and tips are worked out in Python from the gold rows.
every stepdb.py (logged_run)–pipeline_runs One row per step run: when, whether it worked, and what it did or why it failed.

Column-by-column detail for every table is in data_dictionary.pdf.
